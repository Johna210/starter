# Standards: regenerating the scaffolded project's /docs/

The Starter's contribution standard for the doc generator — how the
scaffolded project's `/docs/` is produced from the five-axis
composition (decision 31), and what a contributor changes when the
composition grows.

## The principle

The CLI's materializer writes **both** the workspaces and the docs from
the chosen composition (decision 31). There is exactly **one** source of
truth — the composition — and code + docs are both derived from it.
The scaffolded project's docs are the *generation's* docs
(composition-specific); this Starter repo's `/docs/` is hand-curated,
contributor-facing, and changes as decisions are added.

## What the doc generator produces

`packages/cli/src/materialize/docs.ts` writes the scaffolded project's
`docs/` tree from the composition:

- **`docs/architecture/`** — Mermaid diagrams, composition-specific:
  "your Hono RPC contract spine" (TS shapes) vs "your OpenAPI contract
  spine" (Go shapes, decision 19); the modular monolith; the auth
  subtree; the typed-RPC transport; mobile-auth-flow when mobile is on.
- **`docs/wire-it-in/`** — composition-conditional fences: AI fences
  only when AI is on (decision 20); auth fences in every scaffold
  (auth is always-on).
- **`docs/adr/`** — the convention (empty; the user grows it).
- **`docs/standards/`** — code style (composition-conditional per
  language: Biome for TS, gofmt+golangci-lint for Go, ruff only in
  shape 4), best practices (per seam), anti-patterns.
- **The README** — auto-generated with a "you chose" line, the
  workspace map, and links into `/docs/` (decision 33).

## When to regenerate

There is no standalone "regenerate" step for the *generator* — docs
are materialized every scaffold, so a change to `docs.ts` (or a
template it calls) takes effect on the next scaffold. The workflow:

1. Change the doc templates in `docs.ts` (or add a new one) to match
   the workspace/template change — same composition, same conditional.
2. Materialize a test project locally
   (`npx tsx ci/materialize-test-project.ts /tmp/test-project <shape>`)
   and inspect the generated `/docs/`.
3. The materialize tests assert the docs land where the composition
   says (AI-on scaffolds get `wire-it-in/ai.md`; mobile-on scaffolds
   get `mobile-auth-flow.md`; etc.) — keep them in sync.
4. Mirror the *structure* in this repo's `/docs/` if the change alters
   a domain subdir (decision 30/34): the Starter's docs are the
   contributor-facing rewrite of the same subdirs.

## The mirror discipline (decisions 30, 34)

The recursion is the product: a contributor who learns the `/docs/`
structure once in the Starter repo finds the **same structure** in the
scaffolded project. When the scaffolded project's `/docs/` gains a
subdir or a doc, the Starter repo's `/docs/` mirrors the subdir
(rewritten contributor-facing) — except `contributing/`, which is
Starter-repo-only by design (decision 34's deliberate asymmetry).

## The split in ownership

- **Scaffolded project's `/docs/`** — generated by `docs.ts`,
  composition-conditional, tested by the materialize tests.
- **Starter repo's `/docs/`** — hand-curated, contributor-facing,
  changed *in the same commit* as the decision/template that drives it.
  A template change that isn't mirrored here leaves the recursion
  broken: the Starter's docs describe what the generator *used* to
  produce.
