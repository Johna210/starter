# Contributing: cutting a release

The playbook entry for **"how to cut a release"** (decision 34) — the
deliberate-act flow behind decisions 35/37/38: tag-based, CI-gated,
npm publish. The mechanics of the pipeline are in
[`.github/workflows/release.yml`](../../.github/workflows/release.yml);
this entry is the product-level view: what a release *is* and the
exact steps to cut one.

## The model (decisions 35/37)

- **Releases are deliberate acts**, not side-effects of merge. A
  maintainer cuts a **tag** on `master` when a meaningful set of
  changes is ready; the tag triggers an npm publish of the CLI.
- **The CI matrix must be green before the tag is cut** (decision 37).
  The release pipeline refuses to publish unless the tagged commit's
  most recent CI run is success — a release on a broken matrix is a
  release that breaks the blessed-2×2 envelope.
- **The CLI version and the tag share a version** (decision 35): the
  pipeline verifies `packages/cli/package.json.version == tag`, and
  the CHANGELOG carries a matching entry (decision 38).
- **Pre-1.0 (0.x):** every change is breaking, users re-scaffold to
  upgrade, no migration notes. The 0.x number advances with each
  meaningful release; there's no SemVer bookkeeping — the cadence is
  "when there's something to ship".
- **Post-1.0 (1.0+):** SemVer. Breaking changes require a major bump
  **and** a migration note (`docs/migrations/vX-to-vY.md`, decision
  38); `npx create-fs-starter@1.2.3` pinning is supported.

## How to cut a release (the checklist)

### 1. Bump the version (one source, decision 35)

Edit `packages/cli/package.json` → `version`. That one string is the
single source: the CLI's runtime `VERSION` (`packages/cli/src/version.ts`),
the scaffolded projects' `starterVersion` field, and the tag all read
from it. The pipeline enforces the tag matches it.

Pre-1.0, bump **every** release (e.g. `0.1.0` → `0.2.0`). Post-1.0,
follow SemVer (`1.0.0` → `1.1.0` minor, `2.0.0` major, …).

### 2. Update the CHANGELOG (decision 38)

Move the `[Unreleased]` section's entries into a new
`## [X.Y.Z]` section (fold it into an existing section of the same
version if one already exists, e.g. the initial `0.1.0`), then:

- keep-a-changelog **Added / Changed / Deprecated / Removed / Fixed /
  Security** sections, newest-first;
- flag breaking changes `**BREAKING:**` — **post-1.0 only**, and link
  the migration note from the entry.

Commit the version bump + CHANGELOG together — the pipeline requires
both to reach the tag.

### 3. Post-1.0 breaking change: write the migration note

For a **major** bump (post-1.0 only; pre-1.0 there are no notes —
every 0.x change is breaking by definition, decision 35):

1. Add `docs/migrations/vX-to-vY.md` to the Starter repo (the
   canonical set) — structure: *what changed* → *if you're on X* →
   *if you're on Y* → *verify* (see `docs/migrations/README.md`).
2. Register it in the doc generator's lookup
   (`packages/cli/src/materialize/docs.ts` →
   `migrationNotesFor`) so scaffolds generated by the affected
   versions receive it, keyed on `starterVersion`.

### 4. Cut the tag

```sh
git checkout master && git pull
# … version bump + CHANGELOG commit is on master …
git tag v0.2.0            # vX.Y.Z — must equal package.json's version
git push origin v0.2.0
```

Pushing the tag triggers the Release workflow
(`.github/workflows/release.yml`), which gates:

1. **CI gate** — the tagged commit's most recent CI matrix run must be
   success. If it isn't (or CI is still running), the release fails
   with a message; wait for CI, then re-tag.
2. **Main-branch gate** — the tagged commit must be on `master`
   (decision 37: releases are cut on the Starter repo's main branch);
   a feature-branch tag, even green, is refused.
3. **Version gate** — tag == `packages/cli/package.json` version == a
   `CHANGELOG.md` entry.

### 5. Verify the publish

The pipeline publishes `create-fs-starter` to npm and round-trips the
registry. After it's green:

```sh
npx create-fs-starter@0.2.0 --help        # pinning works (post-1.0; in 0.x latest is the only sensible pin)
npx create-fs-starter --help              # latest
```

## Pinning (decision 37)

- **0.x:** `npx create-fs-starter` pulls `latest`; pinning is
  effectively meaningless because every change is breaking — `latest`
  is the only sensible pin.
- **1.0+:** pinning is supported (`npx create-fs-starter@1.2.3`) and is
  how a user opts out of a breaking change until they're ready.

## What never happens

- Merging to `master` is **not** a release (trunk-based rejected in
  decision 37 — version noise, review short-circuit).
- A tag on a broken matrix (the CI gate is the spine thesis in action:
  a release that breaks the CI matrix breaks the blessed 2×2).
- A tag whose version disagrees with `package.json` or the CHANGELOG —
  the two-artifact release notes are part of the gate, not a
  suggestion.
